# X1Pen: HuBASIC bundle from SLANG-compiler d15d32e (WIDTH rows, KEYLIST/KLIST/KMODE, MML V16 envelope) and the reference review

## Purpose

SLANG-compiler PR #248 is merged at `d15d32eb7c033ca73b8468d1401a2b57fad70979`. X1Pen (main `421e40d`, released as 0.12.0 / x1pen-mcp 2.10.0) bundles hubasic2sl and the x1native runtime from `10cf481e99161fcf1a9b4a2d2b33db327878b47c` (PR #145). This PR does three things:
- replaces the bundle with d15d32e;
- reviews the x1pen-mcp HuBASIC reference (`mcp/reference/hubasic.json`) against d15d32e. The stamp test fails until that is done;
- checks in X1Pen that the new forms convert and run as slang's docs describe, including the PSG registers that `V16` sets.

The reference must:
- `WIDTH`: describe the second argument (rows) and the third and fourth. Rows 25 is accepted silently. Other rows, and any third or fourth argument, give warning HB0705 and are ignored; the screen stays 25 rows. They must be numeric constants (HB0703).
- `KEYLIST n`, `KLIST n`, `KMODE n`: list them as accepted statements that do nothing, so AI does not think they are unusable. A value other than 0 gives warning HB0706. `KEYLIST`/`KLIST` with no number are unsupported (HB0301); `KMODE` with no number is HB0203.
- `PLAY`/`MUSIC`: say plainly that MML volume `V` goes up to 16, and `V16` uses the PSG hardware envelope. ひろしさん expects AI to assume `V15` is the maximum. Also state the digit rule (`V17` is 1, not an error), that the envelope restarts on every note, and that the envelope shape and period come from `SOUND 13` and `SOUND 11`/`SOUND 12`.

Secretary's request says "V16 以上はエンベロープ". The source says only `V16` is the envelope: `V17` and above use the first digit. The reference follows the source, and the report says so.

Rights rule (ひろしさん's): write the reference only from SLANG-compiler sources and `docs/HUBASIC.md` at d15d32e (MIT, ひろしさん's repository) and X1Pen's own code. Never read, copy or paraphrase the HuBASIC manual.

After the PR is open, start the dunedin preview server on the new `dist/` and report how to connect.

Non-goals:
- No version bump (Web, x1pen-mcp, Connector). Bumping and publishing come after the merge, separately.
- No deploy or npm publish; ひろしさん does both.
- No change to the converter or runtime (slang Province's), and no change to the emulator.

## Edge cases and test plan

- Bundle integrity: the importer checks every sha256 and refuses a dirty bundle. `npm run test:hubasic` compares X1Pen's in-browser compile and assemble of the 4 testdata programs with the regenerated fixtures.
- Existing HuBASIC E2E and reference-example tests catch behaviour changes in what X1Pen already does.
  - Risk: a program or example using `KEYLIST`, `KLIST` or `KMODE` as a variable name now fails. Step 3 and a grep of tests and the reference find any.
  - Risk: PLAY programs grow 26 bytes; a test near `$FFE0` or a dataBudget boundary may move. Step 3 finds it.
  - Risk: an existing test that expected `V16` to be error 5. grep finds none today; checked again in step 3.
- State-save reading in the E2E test depends on the internal layout (`PSG0` tag, `register_latch` then `Regs[16]`). The test locates the section by tag and checks its length is at least 20 bytes, so a layout change fails loudly rather than reading the wrong bytes. Polling: the test waits with a timeout for each expected value, so timing jitter does not flake; each note is long enough (seconds) for several polls.
- Reference tests: stamp; catalog (the three new no-op words must be in a dedicated entry's symbols, which input.keys provides); search ranking; every example converts and assembles (the new envelope example included).
- Mutation checks:
  - the new reference test fails if "V16" is removed from the sound summary, or HB0706 from the keys entry;
  - the new E2E test fails against the 10cf481 bundle (`V16` is error 5, and `KEYLIST` alone is not HB0301 there);
  - changing the expected R8 value for V16 fails the E2E test.
- Rollback: revert the PR commit; bundle, fixtures, reference and manifest return together.
- MCP compatibility: published x1pen-mcp 2.10.0 pins 10cf481, so after this merges main mismatches it (advisory `compatible: false`) until the next release bumps both together, as with PR #145.
